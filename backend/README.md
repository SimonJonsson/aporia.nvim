# aporia backend

The Rust process that takes over aporia's agent core, one feature at a time.

## Shape

```
nvim (Lua, permanent)                  aporia (Rust, this workspace)
  UI: floats, keymaps, slash menu        agent loop, provider adapters, streaming
  editor tools: LSP, buffers,   <---->   context assembly, token budget
  diagnostics, :help, treesitter   RPC   sessions (.aporia/), policy checks
```

Lua starts the binary with `jobstart({ "aporia" }, { rpc = true })`. The
transport is msgpack-RPC over stdio, and either side can call the other, so
a Rust tool can call `nvim_*` directly.

- `crates/aporia-core`: the library. Domain model and logic, no Neovim, no
  transport. Everything here is testable with plain `cargo test`.
- `crates/aporia`: the binary. RPC wiring only; it calls into the core.

The split is enforced by Cargo: `aporia-core` does not depend on `tokio`,
`reqwest` or `nvim-rs`, so I/O in the core does not compile.

### Sans-IO core

The core never touches the network, files or Neovim. The agent
(`aporia-core/src/agent.rs`) is a state machine: the shell feeds it inputs
and performs the actions it returns.

```
inputs:  Chunk | ModelEnd | ModelFailed | ToolResult
actions: CallModel { messages, tools } | CallTool(call) | Emit(Output)
outputs: Delta { text, kind } | Done { content } | Error { message, content }
```

The binary is a thin async shell (tokio, nvim-rs, reqwest) that performs
the actions and feeds the results back in. The whole agent loop is tested
with plain synchronous `cargo test`, and every `match` over its states and
inputs is checked by the compiler.

## Reading the code

In this order; each file's module doc says what it is for.

| File | What it is | Rust it shows |
|---|---|---|
| `aporia-core/src/sse.rs` | splits the HTTP body into events | ownership of a buffer, `Option` and `?`, unit tests |
| `aporia-core/src/openai.rs` | the provider's wire format | serde derive, tagged enums, `rename`, borrowing structs (`'a`) |
| `aporia-core/src/agent.rs` | the agent loop | enums as states, `match` on `(state, input)`, `std::mem::take` |
| `aporia-core/src/protocol.rs` | what Lua and Rust say to each other | `#[serde(flatten)]`, defaults |
| `aporia/src/main.rs` | process entry, attaches to Neovim | `#[tokio::main]`, async/await |
| `aporia/src/handler.rs` | RPC methods (`ping`, `chat`, `cancel`) | traits (`Handler`), `Arc<Mutex<_>>`, `tokio::spawn` |
| `aporia/src/turn.rs` | performs one turn's actions | streams, a work queue, error handling without panics |

The Lua half is `lua/aporia/backend.lua` (starts the process, routes
events) and `lua/aporia/tools.lua` (the tools Rust calls back into).

## Strangler fig

The Lua plugin keeps working throughout. Each feature moves like this:

1. Build it in Rust behind the core API, tested against the Lua behaviour
   (fixtures generated by the Lua code, never hand-written).
2. Lua routes that feature to the backend when the binary is built, and
   keeps its own implementation as the fallback.
3. Once the Rust path has been used for real, delete the Lua implementation.

The chat UI is the fixed point. It consumes a reply through one contract,
`request(messages, cb, on_delta)`: `on_delta(text, kind)` for each streamed
piece (`kind` is `"content"` or `"reasoning"`), then `cb(err, content)` once
with everything received. `aporia.http` and `aporia.backend` both implement
it; the backend adds `on_step` for tool progress.

| # | Milestone | Rust you learn | Strangles | |
|---|---|---|---|---|
| 0 | RPC shell, streaming, agent loop, read-only tools | the whole shape | `http.lua` (fallback kept) | done |
| 1 | Session model: round-trip `tests/fixtures/*.json` | ownership, enums + `match`, serde attributes, tests | - | yours |
| 2 | Session store: save, load newest, count, delete all | `std::fs`, `Result` and `?`, an error type (`thiserror`) | `store.lua` | yours |
| 3 | Cancel as an input: `Input::Cancel` ends the turn with what arrived, the shell races it against the stream | `tokio::select!`, channels | - | yours |
| 4 | Retries: back off and retry on 429 and 5xx before failing | loops with state, `tokio::time`, testing time | - | yours |
| 5 | Tool results with structure: tools return JSON, the core summarizes and budgets them | serde_json, traits | - | yours |

Milestone 0 was written for you to read before writing; from 1 on, the Rust
is yours and gets reviewed, not written.

## Milestone 1

Start in `crates/aporia-core/src/session.rs`; its module doc is the brief.
Done means a test in `crates/aporia-core/tests/` that, for every fixture,
deserializes it into your types, serializes it back, and compares the two
as `serde_json::Value`s.

Fixtures come from running aporia's real Lua code paths in a throwaway
project. They cover user turns with text and code-block parts, a teach-mode
trap prompt (text, block, text), open folds, a failed reply and normal
replies. Replies made with the backend also carry `steps` (the tool steps
shown in the chat); the fixtures predate them, so treat `steps` as optional.
